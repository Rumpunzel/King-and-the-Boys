# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"King and the Boys" is a Godot 4 (GDScript, Forward Plus, `config/features` = 4.6) cooperative multiplayer dungeon crawler. Players move their characters through a dungeon that is generated as they explore it, in simultaneous, movement-only turns (actions and combat come later). Multiplayer runs over ENet or Steam (GodotSteam); the host is the referee. The turn system's plan, decisions and progress live in the Claude doc "Turn-Based Behaviour Plan" (https://claude.ai/artifact/L2JbNnrgs7fMqo4o4Cpnkt).

## Running

Use Godot 4.6 (`<godot>` below). Where it is installed on this machine is in `CLAUDE.local.md` (not committed); without one, ask for the path.

- Run game: `<godot> --path .`
- Open editor: `<godot> -e --path .`
- Smoke check (loads autoloads + main scene, prints script errors): `<godot> --headless --path . --quit-after 300`. `--check-only --script` skips autoloads and reports false errors. Don't start a second `--editor` while the user's editor is open.
- Script check: `<godot> --headless --path . res://tests/script_check.tscn` loads every script of ours (not the vendored addons) so each one compiles; the editor scan and the tests only compile what they load.
- New `class_name`s only resolve after an editor rescan (`<godot> --headless --path . --import`, only while the user's editor is closed).
- Headless runs don't print GDScript warnings; the editor does when it reloads scripts.

Assets (meshes, textures, `.blend`) are in Git LFS (~1.7 GB); `.blend` files need a Blender path in the editor settings.

Tests are gdUnit4 suites (`addons/gdUnit4`, `extends GdUnitTestSuite`, `test_*` funcs), split in three: `tests/unit/` (no level, no assets), `tests/integration/` (turn rules on a generated level) and `tests/with_assets/` (equipment and Menagerie suites that load the real meshes). **Only `tests/with_assets/` needs assets** (Git LFS); CI runs it in the manual Asset check, so run it locally after equipment changes. Integration tests build the level from `engine/levels/level.tscn` (the plain level) with the model-free tiles and hero in `tests/fixtures/` (`tests/fixtures/model_free_world.gd`); real profiles hold their model scenes and load meshes and textures with themselves. The fixture profiles are files because spawners replicate structures by their profile's path. Run headless: `<godot> --headless --path . -s res://addons/gdUnit4/bin/GdUnitCmdTool.gd --ignoreHeadlessMode -a res://tests/unit -a res://tests/integration` (exit 0 = pass, 100 = failures); add `-a res://tests/with_assets` with the assets pulled. Asset suites build items with `EquipmentFixtures` (`tests/with_assets/equipment/equipment_fixtures.gd`), restore any cached profile they change, and keep nodes in the tree (`add_child`) so gdUnit does not count orphans; `EditorProperty`/`EditorInterface` code cannot run headless, so test its static helpers. Reports go to `reports/` (gitignored). gdUnit can print a green summary while project scripts fail to compile: also grep for `SCRIPT ERROR`. Test pitfalls: offline, `Player.is_local_player()` is true for every player; Godot treats `append` of two different arrays as the same callable (connect a lambda per array); lambdas copy local variables (share a flag through an array).

Lint: `gdlint .` (gdtoolkit 4.5.0, config in `gdlintrc`, taken from Vagrant: line length 240). Excluded are the vendored addons plus `reports`, `.git` and `.godot`; everything else is linted, including `menagerie`, `tests` and the scripts asset packs ship in `assets/`. gdtoolkit excludes by directory name at any depth, so a folder of ours named like one of those is skipped too. If `gdlint` is not on PATH: `python -m gdtoolkit.linter .`. Don't use `gdformat`.

CI (`.github/workflows/`): **Tests** runs on every push (which covers PR commits): `gdlint`, and `Script check and tests` (script check, then unit and integration tests as separate steps of one job). It needs no Git LFS: the shared setup action (`.github/actions/godot`) leaves `assets/` and `protoype_assets/` out (`.gdignore`) and imports only scripts and small resources. **Asset check** (`asset_check.yml`) runs the main scene with the real assets, only by hand (Actions → Run workflow); run it on `main`, whose caches serve every branch (GitHub drops caches unused for 7 days; then LFS download and import take ~35 min again). CI turns the Blender importer off before importing: without a Blender path, Godot asks how to import `.blend` files and holds back the whole import, so no uid cache is written and every `uid://` path fails. Keep `GODOT_VERSION` in the workflows in sync with `project.godot`. `main` is protected: a pull request merges once `gdlint` and `Script check and tests` passed (no force pushes; merged branches are deleted on GitHub).

## Conventions

- **Game and UI are decoupled.** No gameplay logic or state in UI scripts or scenes: the UI only displays state and forwards the player's intent to game objects (e.g. `PlayerGhost.request_pass`), which own the rules. Settings the UI toggles (e.g. auto-pass) are properties of the game object. UI does not go into game object scenes either: the turn panel lives in the game scene's `UserInterface`, not in `player_ghost.tscn`.
- **The host is the referee.** Clients send requests (RPCs to `Multiplayer.HOST_ID`); the host checks them and changes replicated state. Game state that peers need is replicated by `MultiplayerSynchronizer`s, and each peer turns it into visuals itself.
- **Typed GDScript, strict warnings** (`project.godot`): untyped and inferred declarations and unsafe access/calls are errors. Always use explicit types; put values from untyped `Dictionary`/`Array`s into a typed variable first.
- Node wiring is done through `@export` vars in a "Configuration" export group rather than `$` paths. Many scripts are `@tool`; setters guard with `Engine.is_editor_hint()`.
- References use `uid://` (in scenes, `load()`/`preload()`). `ResourceSaver.save()` outside the editor drops `uid=` attributes, and files it creates have no UID at all: create resources in the editor, or give new `.tres` files a header UID (`ResourceUID.id_to_text(ResourceUID.create_id())`) and check the diff.
- References that leave the editor (spawn data, synchronized properties, RPCs, saves) use `ResourceId` (`client/resources/resource_id.gd`, ported from Vagrant): `ResourceId.of(resource)` gives the file's `uid://…` (plus `::<sub-resource id>` for resources stored inside a file), `ResourceId.find(id)` resolves it and also accepts plain paths. `Files.load_existing()` loads without errors for unknown UIDs. Validate peer-sent IDs through their resolved file path (`ResourceId.get_file_path()`).
- Scripts must not `preload` resources that pull in assets (meshes, textures): scripts would no longer compile without the assets, e.g. in CI. Set such resources in scenes instead (e.g. `Level._wall_tile`).
- A `preload` of a scene that uses the preloading script itself is a load cycle (the scene reports the script as missing): load such scenes on use (see `InputPrompt`, `KeyPrompt`).

## Architecture

**Autoloads** (`project.godot`): `Client` (game start/stop, player names and avatars via the game environment, e.g. Steamworks), `GameConfig`, `Multiplayer` (hosting/joining, `HOST_ID`), `Lobby` (players, spawned as `Player` nodes), `SceneManager` (scene transitions with loading screen), `Panorama`, `PhantomCameraManager`, `ToastParty`.

**Folders**: `client/` (multiplayer, networks, lobby, serialization, game environments), `engine/` (game scene, levels, structures/things/characters and their profiles, player, agents, state machines, turns), `user_interface/` (menus, HUD, turn panel, generic controls like `ToggleButton`, `PlayerAvatar`, `PlayerName`), `data/` (authored resources: levels, tiles, characters, gear, model animations), `assets/` and `protoype_assets/` (LFS), `tests/`, `tools/`. Addons: `menagerie` (ours, editor tool for profiles), the rest vendored (`gdUnit4`, `godotsteam`, `phantom_camera`, `debug_draw_3d`, `toastparty`, `radial_progress`, `godot-git-plugin`, `godot-plugin-refresher`).

**Scene flow**: main menu → multiplayer/lobby menus → `engine/game.tscn` (`Game`: `Level` from `data/levels/level.tscn`, `PlayerGhostSpawner`, `TurnManager`, `Serializer`, `UserInterface`). The host's `Game.setup_game()` builds the level, lets peers sync the turn state and spawns a `PlayerGhost` per player.

**Profiles and spawning**: `Profile` → `StructureProfile` / `ThingProfile` / `CharacterProfile` hold names, stats and model variations; `create()` instantiates the node. Spawners replicate nodes by their profile's resource path. Profiles without model variations give no model (used by the test fixtures); levels, structures and characters work without one.

**Level**: `data/levels/level.tscn` inherits `engine/levels/level.tscn` and adds the dungeon tile set (`DungeonTileSet`), starting and wall tiles, sky and floor. The dungeon is generated around the characters as they move (`Level._build_dungeon_from`); sight follows passages. A tile has a logical `Structure.status` (placed, discovered, revealed), set by the host the moment a step brings it into sight, and a `shown_status` (its look), which every peer catches up through reveal and discover queues, one per character: they wait until the peer has the step that raised the tile (`Character.step_count`, `Structure.status_cause` / `status_cause_step`) and the figure entered its cell. Statuses no step raised show at once.

**Tile decorations**: tile profiles may hold `TileDecorations` (`data/structures/tiles/dungeon_decorations.tres`), which draw from `PropSet`s (`data/structures/props/`: weighted prop scenes plus a scale, like a `DungeonTileSet` for tiles; Polygon Dungeon prefabs). When a tile is first revealed, `Structure._decorate()` adds props as children of its model (edge props along sides without a connection, corner props between two closed sides, clear of the tile spots, collision removed), each wrapped in a `Model` so they drop in one after another with a `ModelAnimation` (`bounce_animation.tres`) once the tile's reveal finished. Architecture is shared with neighbours: an arch is decided by the first of its two tiles to be revealed once the other one exists (even unrevealed; the decorations' `decided_edges` meta prevents doubles), a room pillar by the last of its four room tiles: arches over openings (by chance: often where a corridor meets a room, as a slim arch on two pillars or, about one in three, its ruins; rarely between corridors, as ruins only; both composed from Dungeon Realms pieces in `data/structures/props/archways/`, textured through `PropSet.material_override` with `dungeon_realms_material.tres` since those FBX imports carry no texture; pieces pivoted at one end use `PropSet.center_props`) and pillars on corners with even indices inside rooms (all four cells room tiles, so never beside a doorway's columns; raised by the last of the four to be revealed). `PropSet.prop_scale` is per axis to fit architecture to the 2 m grid. Tiles revealed before they know their level (spawned, loaded) are dressed when `Structure.level` is set. They are picked from the tile's grid position, so every peer shows the same props without syncing. `TileDecorations.walls` can stand walls on some closed sides (edges decided like openings), but the dungeon has none yet: the Dungeon Realms ruin walls were too thick. A shader hiding the walls and arches nearest the camera is still to come.

**Turns** (`engine/turns/turn_manager.gd`, host-authoritative): every character gets `CharacterProfile.speed` moves per turn; all players move at once. `request_move`, `request_undo`, `request_pass`, `request_auto_pass` are RPCs the host checks. Undo goes back to the turn start or the character's last board-changing step (a step that discovered or revealed tiles). A turn ends when every connected player has passed. Characters own their grid state (`grid_cell`, `tile_spot`, `facing`, `movement_points`, `undo_steps`, `step_count`, replicated, owned by the host) and animate their figure locally (`Character._apply_grid_visuals`; quick steps redirect the move under way). Tiles hold up to five pieces on spots set by their profile. `PlayerGhost` is the player: it owns `auto_pass` and the undo/pass actions the turn panel's buttons call (with the actions as shortcuts).

**Haunting** (a player controlling another character, from a previous implementation; `PlayerStateHauntingCharacter` / `...Thing`) is kept but tabled; the player's own character is hidden meanwhile.

**Bodies** (`engine/objects/model/`): characters that wear equipment have a `ModularModel`: `ModularBodyPart`s (mesh instances listing the numbered meshes of a directory, filtered by `_mesh_prefix`, sorted by number; decorative parts may show none, `_related_parts` show while it is hidden) named by the body's own `Part` enum, plus `get_slot_parts(slot)`. Parts no slot owns form the body (hair, faces), rolled by `ModelConfigurationRandom` (`randomized_parts` by name; parts a body lacks are ignored). Two bodies exist:
- `ModularCharacter` (humans, `data/characters/people/modular_character.tscn`): gendered skinned parts from `modular_character.blend`, which saves its meshes to `data/characters/people/meshes/`.
- `DwarfCharacter` (`data/characters/dwarves/dwarf_character.tscn`): one skinned body mesh with the clothes baked in (7 bodies, the TORSO outfit) plus static attachments on `BoneAttachment3D`s (head: hair, beard, beard rings, headwear, face gear; clavicles: shoulder pads). The Dungeon Realms FBX imports save their meshes to `data/characters/dwarves/meshes/<part>/dwarf_<part>_<name>_<NN>.res`, swap their materials for `dwarf_material.tres` (the pack's atlas) and retarget the bodies with `dwarf_bone_map.tres` (the Synty rig, right fingers named `_2`), so the Quaternius animations play. Head attachments need no offset (modelled upright around the bone); the shoulder pads are modelled in the clavicle's original (pre-retarget) space, so they carry that offset, the right one mirrored from the left. All bodies share one skin.
`ModularModelParts.of(scene)` caches what a body scene offers (part names, slot parts, mesh options) for code without an instance. Saved types, catalogs and bodies store parts by number: only append new parts.

**Equipment** (`engine/objects/equipment/`, only modular bodies wear it):
- An `EquipmentLook` (a `Profile`) is a mesh combination that works: `type` + `appearance` (`EquipmentAppearance` → `EquipmentPartMesh`es: part, male mesh, optional female mesh) + an `allowed` flag. Items with stats and abilities will come later as their own resource referencing a look; until then characters wear looks directly.
- Generated looks live in one `EquipmentCatalog` per type (`data/equipment/catalogs/`), each stored inside the catalog under its combination key (`"21-00 00"` → sub-resource ID `21x00_00`, ResourceId `uid://<catalog>::21x00_00`; `00` stands for no mesh, matching the asset pack's bare `00` meshes, so all-`00` keys are empty and never generated). Unchecked looks stay recorded (`allowed = false`) to document the decision; new combinations are added checked, since most work and only odd ones are unchecked by hand. Toggling `allowed` emits no `changed`, so previews do not rebuild. Hand-made looks are files under `data/equipment/<type>/`. Sync and saves send `ResourceId`s; peers may only request allowed looks pointing into `EquipmentLook.ITEM_DIRECTORY`.
- `EquipmentType` (`data/equipment/types/*.tres`) decides the `model` it dresses (a body scene; `fits()`), the `slot`, the `parts` its looks set (numbers of that body's `Part` enum, listed by name in the inspector), `blocked_slots` (e.g. helmets block FACE) and optional `part_groups` (parts sharing a mesh number; the first part leads; `..._LEFT`/`..._RIGHT` pairs are linked automatically). A combination's key is one mesh number per linked group, e.g. `"05 03"` (`EquipmentType.get_combination_key()`). `EquipmentCombinations` walks a type's combinations on a `ModularModel` (leaders, partners keeping their mesh when they lack a number, `show_key()` to put a key back). `EquipmentLook.Slot` is stored by number in saved types: only append new slots.
- Each body decides which parts a slot owns (`ModularModel.get_slot_parts()`, `EquipmentType.get_reset_parts()`). `CharacterEquipment` (child of `Character`) holds one look per slot; equipping resets every part of the slot and its blocked slots, then applies the look, and is refused while another look blocks the slot or once a model is shown the look's type does not fit (dwarf gear on a human). Dwarf types: Dwarf Outfit (TORSO: body + shoulder pads), Dwarf Headwear (hides the hair), Dwarf Face Gear. `Character` re-applies body and equipment on every model rebuild.
- `CharacterProfile` has one starting equipment field per slot (`starting_head` … `starting_off_hand`; the export group hides the prefix), each holding an `EquipmentLook`: usually a copy stored in the profile (`set_starting_equipment_for()` copies looks from other files such as catalogs via `EquipmentLook.make_local()`), so characters are dressed part by part; hand-made look files are referenced. Stored looks are synced by their ResourceId into the profile file (`uid://<profile>::<id>`). Older profiles saved a ResourceId string under the plain slot name; `_set()` loads it as a copy. `random_equipment` rolls one `SpawnTable` per extra look. `create_character_data()` runs on the server only: it resolves the variation, takes the body the player picked in the lobby (`Player.body`, rolled by that player with `CharacterProfile.roll_body()` when picking a character and synced by the Player's synchronizer) if `ModularModel.is_complete_body()` accepts it, else rolls one (`ModelConfigurationRandom.roll()` → `BODY`, mesh IDs; peer-sent IDs are checked by file path against the part's meshes before loading) and equipment (`EQUIPMENT`, look IDs). Character data has 5 keys.
- Sync: `CharacterEquipment.equipped_ids` (`ResourceId`s) is replicated by its own `EquipmentSynchronizer`, pinned to server authority even inside a `PlayerGhost` (client) subtree. Peers call `request_equip()` / `request_unequip()`. There is no ownership/inventory check yet. Saves need nothing extra: spawner data already holds the IDs.
- Authoring happens in Menagerie (`addons/menagerie/`): the Gear tab shows looks grouped by type and base mesh with a checkbox per catalog look (unchecked = greyed; Space toggles the selection; Delete unchecks catalog looks and trashes hand-made files). The Equipment panel lists the types fitting the previewed body and steps through a type's parts (linked parts follow), checks the shown combination (`A`), adds missing combinations (checked), reviews them by keyboard (`Q`/`E` previous/next combination of the varied parts, `A` toggles; needs focus inside the panel), or saves hand-made looks. Toggles only set flags; `CatalogSaver` saves changed catalogs a second later, on leaving the Gear tab and on plugin unload. Characters are dressed in the inspector: a plugin replaces each `CharacterProfile` slot field with `EquipmentSlotProperty`, a type dropdown (types fitting the profile's model variations, `CharacterProfile.fits()`; starting from a copy of the type's first catalog look) plus one carousel per part stepping through that part's meshes (`EquipmentType.get_mesh_options()`, `EquipmentLook.with_part_mesh()`); left/right parts share a carousel until split, and Link matches the right side to the left. Choices go through `emit_changed`, so they can be undone and are saved with the profile; a blocking look empties the slots it blocks. The lobby shows every player's model (others below their portraits) with their synced body and starting equipment (`CharacterProfile.dress_model()`). Character previews keep their rolled body and random equipment across rebuilds, until the model scene changes (`CharacterProfile.setup_model(model, reroll)`); the preview's Randomize re-rolls.
- Design notes and progress: "Equipment Resources Plan" doc (claude.ai, see memory).

Saving: `Serializer` collects `NodeSerializer`s (spawned nodes) and `PropertiesSerializer`s (e.g. `SynchronizerSerializer`: a synchronizer's spawn properties, such as the turn number). Passes are cleared on load (player ids differ between sessions).
