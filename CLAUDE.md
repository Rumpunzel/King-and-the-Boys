# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

"King and the Boys" is a Godot 4 (GDScript, Forward Plus, `config/features` = 4.6) cooperative multiplayer dungeon crawler. Players move their characters through a dungeon that is generated as they explore it, in simultaneous, movement-only turns (actions and combat come later). Multiplayer runs over ENet or Steam (GodotSteam); the host is the referee. The turn system's plan, decisions and progress live in the Claude doc "Turn-Based Behaviour Plan" (https://claude.ai/artifact/L2JbNnrgs7fMqo4o4Cpnkt).

## Running

Use Godot 4.6 (`<godot>` below). Where it is installed on this machine is in `CLAUDE.local.md` (not committed); without one, ask for the path.

- Run game: `<godot> --path .`
- Open editor: `<godot> -e --path .`
- Smoke check (loads autoloads + main scene, prints script errors): `<godot> --headless --path . --quit-after 300`. Quitting while the menu backdrop (`Panorama`) still loads on its thread prints "Failed loading resource" for it and one of its Polygon Dungeon prefabs; harmless (Godot cannot cancel a threaded load), and likelier right after heavy runs. `--check-only --script` skips autoloads and reports false errors. Don't start a second `--editor` while the user's editor is open.
- Script check: `<godot> --headless --path . res://tests/script_check.tscn` loads every script of ours (not the vendored addons) so each one compiles; the editor scan and the tests only compile what they load.
- New `class_name`s only resolve after an editor rescan (`<godot> --headless --path . --import`, only while the user's editor is closed).
- Headless runs don't print GDScript warnings; the editor does when it reloads scripts.

Assets (meshes, textures, `.blend`) are in Git LFS (~1.7 GB); `.blend` files need a Blender path in the editor settings.

Tests are gdUnit4 suites (`addons/gdUnit4`, `extends GdUnitTestSuite`, `test_*` funcs), split in three: `tests/unit/` (no level, no assets), `tests/integration/` (turn rules on a generated level) and `tests/with_assets/` (equipment and Menagerie suites that load the real meshes). **Only `tests/with_assets/` needs assets** (Git LFS); CI runs it in the manual Asset check, so run it locally after equipment changes. Dungeon generation is checked over many seeds by `tests/fixtures/dungeon_rules.gd` (passages both ways, restrictions, extents, closed outer wall; failures name their seed): model-free in `tests/integration/levels/`, with the real tiles and their restrictions in `tests/with_assets/levels/`. Integration tests build the level from `engine/levels/level.tscn` (the plain level) with the model-free tiles and hero in `tests/fixtures/` (`tests/fixtures/model_free_world.gd`); real profiles hold their model scenes and load meshes and textures with themselves. The fixture profiles are files because spawners replicate structures by their profile's path. Run headless: `<godot> --headless --path . -s res://addons/gdUnit4/bin/GdUnitCmdTool.gd --ignoreHeadlessMode -a res://tests/unit -a res://tests/integration` (exit 0 = pass, 100 = failures); add `-a res://tests/with_assets` with the assets pulled. Asset suites build items with `EquipmentFixtures` (`tests/with_assets/equipment/equipment_fixtures.gd`), restore any cached profile they change, and keep nodes in the tree (`add_child`) so gdUnit does not count orphans; `EditorProperty`/`EditorInterface` code cannot run headless, so test its static helpers. Reports go to `reports/` (gitignored). gdUnit can print a green summary while project scripts fail to compile: also grep for `SCRIPT ERROR`. Test pitfalls: offline, `Player.is_local_player()` is true for every player; Godot treats `append` of two different arrays as the same callable (connect a lambda per array); lambdas copy local variables (share a flag through an array).

Lint: `gdlint .` (gdtoolkit 4.5.0, config in `gdlintrc`, taken from Vagrant: line length 240). Excluded are the vendored addons plus `reports`, `.git` and `.godot`; everything else is linted, including `menagerie`, `tests` and the scripts asset packs ship in `assets/`. gdtoolkit excludes by directory name at any depth, so a folder of ours named like one of those is skipped too. If `gdlint` is not on PATH: `python -m gdtoolkit.linter .`. Don't use `gdformat`.

CI (`.github/workflows/`): **Tests** runs on every push (which covers PR commits): `gdlint`, and `Script check and tests` (script check, then unit and integration tests as separate steps of one job). It needs no Git LFS: the shared setup action (`.github/actions/godot`) leaves `assets/` and `protoype_assets/` out (`.gdignore`) and imports only scripts and small resources. **Asset check** (`asset_check.yml`) runs the main scene with the real assets, only by hand (Actions → Run workflow); run it on `main`, whose caches serve every branch (GitHub drops caches unused for 7 days; then LFS download and import take ~35 min again). CI turns the Blender importer off before importing: without a Blender path, Godot asks how to import `.blend` files and holds back the whole import, so no uid cache is written and every `uid://` path fails. Keep `GODOT_VERSION` in the workflows in sync with `project.godot`. `main` is protected: a pull request merges once `gdlint` and `Script check and tests` passed (no force pushes; merged branches are deleted on GitHub).

## Conventions

- **Game and UI are decoupled.** No gameplay logic or state in UI scripts or scenes: the UI only displays state and forwards the player's intent to game objects (e.g. `PlayerController.request_pass`), which own the rules. Settings the UI toggles (e.g. auto-pass) are properties of the game object. UI does not go into game object scenes either: the turn panel lives in the game scene's `UserInterface`, not in `player_controller.tscn`.
- **The host is the referee.** Clients send requests (RPCs to `Multiplayer.HOST_ID`); the host checks them and changes replicated state. Game state that peers need is replicated by `MultiplayerSynchronizer`s, and each peer turns it into visuals itself.
- **Typed GDScript, strict warnings** (`project.godot`): untyped and inferred declarations and unsafe access/calls are errors. Always use explicit types; put values from untyped `Dictionary`/`Array`s into a typed variable first.
- Every script with a `class_name` (tests aside) has an `@icon` from `tools/icons/` (by `uid://`), coloured by area: red for game objects (characters, gear, structures, model animations), white for systems and nodes (client, turns, player), green for UI and Menagerie, yellow for data (configurations, spawn tables, catalogs); families share one. Icons are 32 px recoloured copies from the full game-icons.net set in `tools/game_icons/` (CC BY 3.0, see its README): each new one gets a row in `tools/icons/CREDITS.md`. CI leaves `tools/game_icons/` out of its import.
- Node wiring is done through `@export` vars in a "Configuration" export group rather than `$` paths. Many scripts are `@tool`; setters guard with `Engine.is_editor_hint()`.
- References use `uid://` (in scenes, `load()`/`preload()`). `ResourceSaver.save()` outside the editor drops `uid=` attributes, and files it creates have no UID at all: create resources in the editor, or give new `.tres` files a header UID (`ResourceUID.id_to_text(ResourceUID.create_id())`) and check the diff.
- References that leave the editor (spawn data, synchronized properties, RPCs, saves) use `ResourceId` (`client/resources/resource_id.gd`, ported from Vagrant): `ResourceId.of(resource)` gives the file's `uid://…` (plus `::<sub-resource id>` for resources stored inside a file), `ResourceId.find(id)` resolves it and also accepts plain paths. `Files.load_existing()` loads without errors for unknown UIDs. Validate peer-sent IDs through their resolved file path (`ResourceId.get_file_path()`).
- Scripts must not `preload` resources that pull in assets (meshes, textures): scripts would no longer compile without the assets, e.g. in CI. Set such resources in scenes instead (e.g. `Level._wall_tile`).
- A `preload` of a scene that uses the preloading script itself is a load cycle (the scene reports the script as missing): load such scenes on use (see `InputPrompt`, `KeyPrompt`).

## Architecture

**Autoloads** (`project.godot`): `Client` (game start/stop, player names and avatars via the game environment, e.g. Steamworks), `GameConfig`, `Multiplayer` (hosting/joining, `HOST_ID`), `Lobby` (players, spawned as `Player` nodes), `SceneManager` (scene transitions with loading screen; the host's `transition_everyone_to()` sends every connected peer to a scene and waits for those it sent, minus peers that leave: `confirm_transition(scene_path)`, `transition_progressed`, `transition_completed`, `tell_transitioning_peers()`, `end_transition()`; a scene that fails to load drops the transition with `scene_load_failed`, and in a multiplayer game that peer leaves, or the host stops hosting, and returns to the main menu), `Panorama` (the menus' 3D backdrop: `user_interface/menus/menu_background.tscn`, the Polygon Dungeon demo with a `DriftingCamera` instead of its keyframed wobble), `PhantomCameraManager`, `ToastParty`.

**Folders**: `client/` (multiplayer, networks, lobby, serialization, game environments), `engine/` (game scene, levels, structures/things/characters and their profiles, player, agents, state machines, turns), `user_interface/` (menus, HUD, turn panel, generic controls like `ToggleButton`, `PlayerAvatar`, `PlayerName`), `data/` (authored resources: levels, tiles, characters, gear, model animations), `assets/` and `protoype_assets/` (LFS), `tests/`, `tools/`. Addons: `menagerie` (ours, editor tool for profiles), the rest vendored (`gdUnit4`, `godotsteam`, `phantom_camera`, `debug_draw_3d`, `toastparty`, `radial_progress`, `godot-git-plugin`, `godot-plugin-refresher`).

**Scene flow**: main menu → multiplayer/lobby menus → `engine/game.tscn` (`Game`: `Level` from `data/levels/level.tscn`, `PlayerControllerSpawner`, `TurnManager`, `Serializer`, `UserInterface`). The host's `Game.start_hosted_game()` waits until every peer sent to the game scene shows it ("Waiting for players [ready / sent]"; peers that leave drop out, peers joining meanwhile are not waited for), then `Game.setup_game()` builds the level (`Level.built`) and has `PlayerControllerSpawner` spawn a `PlayerController` per player, each created on its own free spot of the start tile so no figure moves there (once it is full, on the nearest revealed tile with room along passages, `Level.get_nearest_free_spot_position()`, which `Character._ready` also uses for any character spawned onto a full tile) (`start_synching_players()` waits until its level `is_built`, also spawns players who join later, and is safe to call again, e.g. after loading). Then the host waits until every peer it sent has reported (`Game._report_ready`) that its own character and the tile under it arrived (`Level.tile_placed`), so nobody starts in a half-empty level, and ends every loading screen at once ("Placing players [ready / sent]"). Every peer gets the turn state once it reports (`TurnManager.start_syncing_peer`). Players joining the running game keep their loading screen (the game scene is in `SceneManager.KEEPS_JOINERS_LOADING`) until they report the same; the host then lifts it.

**Profiles and spawning**: `Profile` → `StructureProfile` / `ThingProfile` / `CharacterProfile` hold names, stats and model variations; `create()` instantiates the node. Spawners replicate nodes by their profile's resource path. Profiles without model variations give no model (used by the test fixtures); levels, structures and characters work without one. Characters, structures and things are `BoardObject`s (`engine/objects/board_object.gd`, an abstract `Node3D`: each keeps its own typed `profile` and hands it out through `get_profile()`; the base shows the profile's model by `variation` (rolled once on the host, by the spawners or `CharacterProfile.create_character_data()`, and sent with the spawn data, so every peer shows the same model), calls `_on_model_added()` for each new model, and gives portrait and heads-up anchor), not physics bodies: tweens move every figure and the grid answers where things are (e.g. reach, `Level.get_cells_in_reach()`), so pieces have no collision shapes and the project no physics layers (props lose their colliders as tiles dress them; the camera still uses physics interpolation); a `HitBox` is a plain node on a piece that holds who controls it. Their transforms are sent only as they spawn: each peer moves characters by their grid state, and turns the thing on a turned tile itself (`Level._on_tile_turned`).

**Level**: `data/levels/level.tscn` inherits `engine/levels/level.tscn` and adds the dungeon tile set (`DungeonTileSet`), starting and wall tiles, sky and floor. The dungeon is generated around the characters as they move (`Level._build_dungeon_from`); sight follows passages. Tiles are drawn by weight from `DungeonTileSet.pick_tile()` with the host's `Level.generation_random` (seeded, the same seed builds the same dungeon for the same order of exploration; its state is not saved yet) among those keeping the most of their neighbours' connection restrictions, all of them wherever one can; where none keeps them all, the cell is recorded in `Level.restriction_fallbacks` (e.g. treasure dead ends want empty space where the dungeon later grows). A tile's shape is its `Structure.get_openings()` (the profile's connections, turned); `get_connections()` adds, for a room tile, every side towards a placed tile of its room type: tiles of one room type side by side always connect, so the picker lets a room tile fit beside its own type whatever its shape (`TileBlueprint.fits()`). Each revealed tile outside rooms shows a worn sandy path to every opening (a strip on its floor drawn by `worn_path.gdshader` with the prototype `desert_ground_01` textures; room tiles take `TileDecorations.room_path_material`, fainter flagstones (`room_path_material.tres`, `ground_tiles_01`) towards their exits, as walls shape them more than openings) (`TileDecorations.create_paths()`, a child of its model) and planks lie over every gap where two tiles open to each other, unless they are one room (`TileDecorations.bridges`; local, laid by each peer: `Level._bridges` by gap, `_update_gaps_of()` lays or takes up only the bridges on one tile's sides, so the others never drop in again). None lead onto a lifted tile until it has landed (`Structure.is_settled()`, `landed`); how a lifted tile rises, wobbles, spins and drops, the dust it raises lifting and landing and the magic sparkles and glow under it while it hangs (`data/structures/props/lift/`), is `Level.tile_lift_animation` (`TileLiftAnimation`, `data/model_animations/tile_lift_animation.tres`, set in the dungeon level scene as its particles are assets; shown by `TileLift`, which stops a spin under way whenever the tile turns, so the model never spins again on being set down). Tiles leaving the level (e.g. a save being loaded) leave its registries with their bridges (`Level._forget_tile`), as things do. A tile has a logical `Structure.status` (placed, discovered, revealed), set by the host the moment a step brings it into sight, and a `shown_status` (its look), which every peer catches up through reveal and discover queues, one per character: they wait until the peer has the step that raised the tile (`Character.step_count`, `Structure.status_cause` / `status_cause_step`) and the figure entered its cell, then `ModelAnimation.reveal_delay` of its move; what a turned tile brings into sight waits `TileLiftAnimation.reveal_delay` from the moment it turns (as it is set down, its drop starting, or as a turn is undone; `Level._hold_reveals_on()`), and the figures on it ride the drop or spin (`Character.carry_on()`, finishing a step under way first), as does the thing on it, by its model only (the thing itself turns at once, on every peer). A revealed tile discovers its neighbours only across passages (both sides open), like sight. Statuses no step raised show at once.

**Tile decorations**: tile profiles may hold `TileDecorations` (`data/structures/tiles/dungeon_decorations.tres`), which draw from `PropSet`s (`data/structures/props/`: weighted prop scenes plus a scale, like a `DungeonTileSet` for tiles; Polygon Dungeon prefabs). When a tile is first revealed, `Structure._decorate()` adds props as children of its model (edge props along sides without a connection, corner props between two closed sides, clear of the tile spots, collision removed), each wrapped in a `Model` so they drop in one after another with a `ModelAnimation` (`bounce_animation.tres`) once the tile's reveal finished; prop sets may bring their own `drop_animation` (architecture falls in from above with `drop_animation.tres`, a `ModelDropAnimation`, before the clutter, dithering in through the occludable shader's `fade` instance uniform). Architecture is shared with neighbours: an arch is decided by the first of its two tiles to be revealed once the other one exists (even unrevealed; the decorations' `decided_edges` meta prevents doubles), a room pillar by the last of its four room tiles: arches over openings (by chance: often where a corridor meets a room, as a slim arch on two pillars or, about one in three, its ruins; rarely between corridors, as ruins only; both composed from Dungeon Realms pieces in `data/structures/props/archways/`, textured through `PropSet.material_override` with `dungeon_realms_material.tres` since those FBX imports carry no texture; pieces pivoted at one end use `PropSet.center_props`) and pillars on corners with even indices inside rooms (all four cells room tiles, so never beside a doorway's columns; raised by the last of the four to be revealed). `PropSet.prop_scale` is per axis to fit architecture to the 2 m grid. Tiles revealed before they know their level (spawned, loaded) are dressed when `Structure.level` is set. They are picked from the tile's grid position, so every peer shows the same props without syncing. Lights (`dungeon_lights.tres`: composed torch, brazier and candle scenes in `data/structures/props/lights/` with Polygon Particle FX fire and a shadowless warm `OmniLight3D`; the particle nodes use `local_coords` so their scale applies) stand now and then in the middle of a closed side; rarely a cluster of glowing crystals stands in a corner between two closed sides instead of a corner prop (`TileDecorations.corner_lights`, `crystals.tres`, scenes in `data/structures/props/crystals/`, `crystal_material.tres`: the occludable shader's `saturated_glow` lets the coloured parts glow). Flames' lights are `FlickeringLight`s (`engine/objects/structures/flickering_light.gd`: energy wavers by noise; crystals pulse slowly), and every candle in the clutter is lit (`lights/lit_*.tscn`). Doorway arches face the room (`TileDecorations._facing_room()`), so the torch-lit arch (`archways/pillar_arch_torches_01.tscn`) hangs its torches on the room side. Rooms as a whole: `Level.get_room_cells()` follows connections between tiles of one room type (rooms are built whole, `Level._build_room_from`; `is_room_complete()` tells peers still receiving tiles, loading or joining). Now and then a room gets a centrepiece, a sarcophagus or a dwarven throne (`Level._room_centrepieces` = `data/things/centrepiece_spawn_table.tres`, `data/things/centrepieces/`): the host rolls it per room as the room is built (seeded by the room, so rebuilding on every step changes nothing) and spawns it, unrevealed, on the grid corner nearest the room's middle whose four cells are in the room and which holds no pillar (`Level.get_centrepiece_corner()`, so rooms need 2x2 cells; not while a figure stands on one of the four tiles); each peer reveals it with its own view of those tiles. Things on corners are kept in `Level._corner_things` (by corner index, recognised by their position), take the spot towards them on each of their four tiles (`get_free_spots`), show with the first of those tiles, and catch the eye of figures there (`get_thing_near`). They are things (not decorations) so they can become interactable; their Dungeon Realms FBX imports map their materials to `dungeon_realms_material.tres`, and they fall in with the drop animation. Room tiles get rugs (`room_rugs.tres`, turned at random: one fitting the tile diagonally fits at any angle; dust turns too, sun beams keep their slant) and ambience (`room_ambience.tres`: sun beams with a spot light; scenes in `data/structures/props/ambience/`); dust (`room_dust.tres`) is rolled per room (`TileDecorations.dusty_room_chance`, seeded by the room's first cell) and then drifts over every tile of it. `material_override` applies to every mesh of a collection, so other packs go into sub-collections: `PropSet.collections` are picked by weight like props, each with its own scale and material (e.g. `dwarven_clutter.tres` and `dwarven_storage.tres`, Dungeon Realms, inside the dungeon clutter and storage). `TileDecorations.walls` can stand walls on some closed sides (edges decided like openings), but the dungeon has none yet: the Dungeon Realms ruin walls were too thick. Each revealed tile stands on ground (`TileDecorations.create_ground()`, `engine/objects/structures/tile_ground.gdshader`): it reaches past the tile through its openings only (the instance uniform `open_sides`), towards the neighbours it connects to, fraying into the table, and stays close along closed sides and at corners; a contact shadow runs along the tile, and its texture lies in world space so neighbours' patches merge (`data/structures/props/ground/`: tiled stone under rooms, spanning whole sides and reaching further so a room stands on one patch; rocky dirt under corridors, narrowing to a tongue). It hangs on the structure, not its model, so it stays on the table while the tile lifts. The dungeon's border (the wall tile, `data/structures/tiles/wall.tscn`) closes it fully: one of Polygon Dungeon's square rock piles per cell, each scaled to fill the cell, picked and turned by the cell (`engine/objects/structures/cave_wall.gd`; the cave pieces left gaps), on `data/structures/props/polygon_dungeon_material.tres` (the occludable shader on that pack's atlas), so it dithers away too. Architecture fades where it hides the player: `dungeon_realms_material.tres` is a `ShaderMaterial` on `engine/objects/structures/occludable.gdshader`, which dithers away fragments near the line from the camera to the global shader parameter `occlusion_target` (project setting); `OcclusionTarget` in `player_controller.tscn` sets it to the local player's figure every frame. Shadow passes are left whole.

**Look**: the dungeon stands on a tabletop (the cloth under `data/levels/level.tscn`) and is lit as a miniature diorama: deep, warm darkness with warm lights in it, and a light 4 m above the player's character (`CharacterLight` under `Character` in `player_controller.tscn`, `engine/objects/characters/character_light.gd`): cool blue of its own, so figures shine without carrying a light, or the colour, energy and range of the brightest light the character carries (`Character.get_light_sources()`, `light_sources_changed`), so a torch lights the ground around its bearer as a light from above would. Its own blue gives way where flames already light the figure (the `FlickeringLight`s in `FlickeringLight.GROUP`, `get_light_at()`), so torches beside it keep their warm colour, and it lights no fog (fog between the camera and the figure would glow in front of it). A carried light is a `LightSource` (`engine/objects/characters/light_source.gd`, files in `data/equipment/light_sources/`): a mesh naming one in its `LightSource.META` (the torch), or an ability's (`Ability.get_light_source()`, the rogue's lantern). Lights widen sight: `Character.get_vision()` / `get_dark_vision()` (used by `Level` for what a hero reveals and discovers; the host's `Level.follow_sight_of()` updates a hero's sight as it steps and as its lights change, so a torch equipped or a lantern lit shows what it brings into sight at once; a light carried twice counts once) apply each carried light's `vision_modifiers` / `dark_vision_modifiers` to the profile's values, `StatModifier`s (`engine/objects/characters/modifiers/`: one strategy each, `AddStatModifier`, `MultiplyStatModifier`; lists apply in order). The torch and the lantern add a cell to each. `data/levels/dungeon_environment.tres` sets the dim warm ambient, AgX tone mapping, SSAO, glow (lights and emissive parts brighter than 1 bloom), depth fog darkening the far table, volumetric fog (thin, warm: carried lights glow as a haze around their bearers), and a stronger contrast. The level's `WorldEnvironment` holds a tilt-shift by distance across the floor (`engine/levels/focus_blur.gd`, a `CompositorEffect` in its `Compositor`, with `focus_blur.glsl` and `focus_copy.glsl`): after the transparent pass it rebuilds each pixel's world position from depth and blurs by its horizontal distance from the focal point, where the camera's centre ray meets the floor (under the player's figure), so all that stands near the figure stays sharp at any height, unlike depth of field, which measures from the camera. Without a rendering device (headless) it does nothing. The project uses 4× MSAA plus SMAA and debanding. Treasure chests glow from inside (`data/things/treasure_light.tscn`: a shadowless, slowly pulsing `FlickeringLight` in the chest's middle, set per chest scene, small enough to seep out only around the chest, with a few rising gold glints). Coloured dust motes (`data/levels/dust_motes.tscn`: amber, gold, rose and a few teal, unshaded and brighter than 1) drift over the whole table, so the tilt-shift turns those at the screen's edges into bokeh. The tile under the local player is marked by `engine/turns/tile_highlight.gdshader`: four thin glowing corner brackets that breathe, blooming through the glow.

**Debug drawings**: F3 (`toggle_debug_drawings`) toggles `LevelDebug` (a node of the plain level), which draws every frame while shown, on this peer only: an outline around every room (`Level.get_rooms()`, in its room type's colour, lightened, labelled with its name and size, with its centrepiece corner) and each revealed tile's connection restrictions (`Structure.draw_debug()`: green may connect, brown may not, blue where the neighbour placed does not fit), and the tiles' labels with their name and grid position (`Structure.show_debug_label()`; hidden otherwise, `Structure.debug_labels_shown` for tiles placed later). Add further debug drawings there, so the one key shows and hides them all.

**Turns** (`engine/turns/turn_manager.gd`, host-authoritative): every character gets `CharacterProfile.speed` moves per turn; all players move at once. `request_move`, `request_undo`, `request_pass`, `request_auto_pass` are RPCs the host checks. Undo goes back to the turn start or the character's last board-changing step (a step that discovered or revealed tiles). A turn ends when every connected player has passed. Moves, undo and spawning play `ModelAnimation`s, tweens on the whole model (`data/model_animations/`: the hop of `miniature_move_animation.tres`, the bounce of `high_bounce_animation.tres`); each may name animations to go with it (`body_animation` as it starts, `body_landing` at `body_landing_time`, `body_follow_up` after it; with delays, start offsets, speeds and blend times), and how the figure travels (`travel_transition`, `travel_ease`, `travel_delay`; redirected moves use `redirect_*`). Animations are files: every Quaternius animation is saved to `data/characters/animations/quaternius/` (Universal Animation Library 1, `assets/quaternius_animations/UAL1.glb`; the `_RM` files from its root-motion export `UAL1_RM.glb`, which is not in the repository) and `quaternius_2/` (Universal Animation Library 2, `UAL2.glb`: sword combos, shield, bow, hits, chests and zombies); the files are copies, free to edit, not tied to the import, and `Model` plays any `Animation` file by adding it to a `body` library on its `AnimationPlayer` (its child named so unless `_animation_player` is set; models driven by an `AnimationTree` skip them); both rigs share the bone names, so every file plays on every body. Both libraries share the Unreal mannequin rig, which their imports retarget to Godot's humanoid bone names (`retarget/bone_map`); the mannequin's fingertip `*_04_leaf_*` tracks are left out of the copies. To take a new release of a library, replace each file's animation but keep its UID, its loop mode and tracks the source lacks (e.g. the method keys of `Sword_Exit`/`Sword_Enter`). The shared tweens (`miniature_move_animation.tres`, `high_bounce_animation.tres`) name no animation files, as `CharacterProfile` preloads them and scripts must not pull in asset files; each hero has their own move and spawn (`data/model_animations/heroes/`). A model rests in `BodyAnimations`, a state: an `entry` played once going in, a list of animations (in sequence, one picked at random each time it comes to rest, or a new one at random every cycle) and an `exit` played once leaving it: its idles (`CharacterProfile.idle_animations`, set on every model the profile creates; its autoplay without), or what `Model.rest_in()` chose (through the exit of the state it leaves and the entry of the new one). Passing shows too: `TurnManager.passed_players_changed` reaches every peer, `PlayerController` calls `Character.show_passed()`, and the model rests in the profile's `passed_animations` (e.g. sitting down, sitting, getting up) until the pass ends. While a held ability is in use (`Character.active_ability_id`, replicated) the model rests in its `Ability.cast_animations` instead (the Mystic's Turn Tile: Spell_Double enter, idle, exit); `Character._get_rest()` decides. In the lobby a character shows off as a player picks it (`CharacterProfile.selected_animation`, played by `LobbyMenu` on every peer when it builds the model; R picks another character at random). Characters own their grid state (`grid_cell`, `tile_spot`, `facing`, `movement_points`, `undo_steps`, `step_count`, replicated, owned by the host) and animate their figure locally (`Character._apply_grid_visuals`; quick steps redirect the move under way). Tiles hold up to five pieces on spots set by their profile. `PlayerController` is the player: it owns `auto_pass` and the undo/pass actions the turn panel's buttons call (with the actions as shortcuts).

**Taking control** (a player controlling another character or thing, from a previous implementation; `PlayerStateControllingCharacter` / `...Thing`, `AgentStateControlled`) is kept but tabled; the player's own character is hidden meanwhile. The host decides: clients ask with `HitBox.request_control()` / `request_release()`, the host checks `may_be_controlled_by()` (the asker's own character, controlling nothing yet, within its reach: standing on its tile or the next one along a passage, `PlayerController.can_reach()` with `Level.get_cells_in_reach()` and `Level.get_cells_of()`, where a thing on a grid corner stands on all four cells, a piece no one controls that is no player's own character) and sets `HitBox.controller` (and `Character.controlling`) on every peer; the client enters its controlling state only once that arrives, and a controller that leaves gives its piece back. Nothing offers a piece to control yet (the interaction area that did is gone, as the game is grid-based): `PlayerStateMachine.handle_interactable()` takes the piece a grid-based finder will hand it, `InputPrompt`s show its interactions, and `engine/player/materials/highlight_material.tres` (the outline the area put on it) waits for it too.

**Bodies** (`engine/objects/model/`): characters that wear equipment have a `ModularModel`: `ModularBodyPart`s (mesh instances listing the numbered meshes of a directory, filtered by `_mesh_prefix`, sorted by number; decorative parts may show none, `_related_parts` show while it is hidden) named by the body's own `Part` enum, plus `get_slot_parts(slot)`. Parts no slot owns form the body (hair, faces), rolled by `ModelConfigurationRandom` (`randomized_parts` by name; parts a body lacks are ignored; `mesh_pools` limits a part to some mesh numbers, `"00"` for none; a part without a pool rolls from all; in the inspector Menagerie shows every body part with a thumbnail per mesh to switch in and out of its pool, `BodyPoolsProperty`; the thumbnails are rendered on the body's head by `body_part_thumbnails.gd`, which waives culling, as skinned meshes keep their bounds in their own space). Menagerie's preview has a carousel per body part under its Randomize button, stepping through what the part may show for the profile (`CharacterProfile.get_body_options()`, kept for the preview by `set_preview_body_part()`), and buttons playing the character's selection, spawn, move, undo and pass animations. Each hero has its own (`data/characters/people/<hero>_body.tres`, e.g. the knight's groomed beards, the mystic's long ones), and the server only takes a lobby body that keeps to the profile's pools (`allows()`). Two bodies exist:
- `ModularCharacter` (humans, `data/characters/people/modular_character.tscn`): gendered skinned parts from `modular_character.blend`, which saves its meshes to `data/characters/people/meshes/`. A hero's gender is part of their body configuration (`ModelConfigurationRandom.gender`, e.g. the elf is female), set by `CharacterProfile.create_model()` on every model before a body is rolled or applied (`ModularModel.set_gender()`: each `ModularBodyPartGendered` lists the other gender's meshes and keeps its mesh number where it can; female bodies have no facial hair), so pools hold that gender's mesh numbers and Menagerie shows them (`ModularModelParts.of(scene, gender)`, the thumbnails); equipment looks carry a female mesh per part where one exists.
- `DwarfCharacter` (`data/characters/dwarves/dwarf_character.tscn`): one skinned body mesh with the clothes baked in (7 bodies, the TORSO outfit) plus static attachments on `BoneAttachment3D`s (head: hair, beard, beard rings, headwear, face gear; clavicles: shoulder pads). The Dungeon Realms FBX imports save their meshes to `data/characters/dwarves/meshes/<part>/dwarf_<part>_<name>_<NN>.res`, swap their materials for `dwarf_material.tres` (the pack's atlas) and retarget the bodies with `dwarf_bone_map.tres` (the Synty rig, right fingers named `_2`), so the Quaternius animations play. Head attachments need no offset (modelled upright around the bone); the shoulder pads are modelled in the clavicle's original (pre-retarget) space, so they carry that offset, the right one mirrored from the left. All bodies share one skin. Gear is repainted in its character's colours (`CharacterProfile.gear_primary_color` for the packs' blue highlights, `gear_secondary_color` for their gold; set on every model the profile creates, `ModularModel.set_gear_colors()`): gear parts take the `ShaderMaterial` of their atlas (`ModularModel._gear_materials`: `data/characters/gear/hero_gear_material.tres`, found by Fantasy Hero's `Mask_01`, and `dwarf_gear_material.tres`, found by its key colours, as Dungeon Realms has no masks; both on `engine/objects/model/gear_colors.gdshader`) with the colours as instance uniforms. The same materials paint skin and hair: a body rolls a skin and a hair colour from its configuration (`ModelConfigurationRandom.skin_colors` / `hair_colors`; none keeps the atlas' own), carried in the body dictionary under `ModularModel.BODY_SKIN_COLOR` / `BODY_HAIR_COLOR` next to the part numbers (so it reaches peers and saves with the body, and the server only takes colours from the lists) and shown by `ModularModel.set_body_colors()`. Every part takes the skin colour (gear shows bare hands); only a body's `get_hair_parts()` take the hair colour, as the dwarves' outfits share their hair's dark brown (so their eyebrows, baked into the body mesh, keep it). Fantasy Hero finds skin (with stubble and lips) by `Mask_03` and hair by `Mask_04`; the dwarf atlas by key colours. Each hero has a colour of their own (`Profile.color`), and menu previews move a model by its profile's `preview_offset` (the dwarf stands higher).
Both bodies hold weapons and shields the same way: decorative parts on `BoneAttachment3D`s of the hands (`MAIN_HAND` and `TWO_HANDED` on `RightHand`; `OFF_HAND`, the shield on the forearm, and `OFF_HAND_WEAPON`, a one-handed weapon in the left hand's grip, on `LeftHand`; both rigs use the humanoid bone names) listing shared meshes in `data/equipment/meshes/<part>/` (`OFF_HAND_WEAPON` lists the main hand's, so either hand holds every one-handed weapon; its grip and stow are the main hand's mirrored across the skeleton's rest pose, so a second blade or a torch is held like the first) (the Dungeon Realms `SM_Wep_*` FBX imports save them there as `weapon_<kind>_<NN>.res` with `dwarf_material.tres`, the Modular Fantasy Heroes `SK_Wep_*` ones, sheaths left out, as `weapon_hero_<kind>_<NN>.res` with `data/characters/people/fantasy_hero_material.tres`; numbered per part, new meshes take the next numbers). Both packs' weapons are pivoted at the grip and point along +Y, so one transform per part holds them all (a quarter turn about Z puts them through the fist). A mesh may bring a scene along (meta `ModularBodyPart.ATTACHMENT_META`, a `PackedScene`), which the part shows on itself while it shows that mesh, hidden while stowed: the torch (`data/equipment/meshes/main_hand/weapon_torch_39.res`, Polygon Dungeon's torch stick scaled to a hand torch, a one-handed weapon for either hand) brings `data/equipment/attachments/torch_fire.tscn` (its fire, kept upright by `engine/objects/model/upright.gd` however the hand holds it). The elf starts with one in the off hand (Off-Hand Weapon); its flame carries no light of its own, the character's light above takes the torch's (`data/equipment/light_sources/torch.tres`). The rogue carries a lantern on his belt instead, lit or put out by his Lantern ability (`ToggleLightAbility`, `data/abilities/lantern.tres`: free, starts lit, and stays done: its step opts out of the undo stack (`AbilityStep.can_be_undone()`), leaving earlier steps undoable; `Character.toggled_ability_ids` replicates the toggles differing from their start; the ability hangs its `prop` (`data/characters/props/belt_lantern.tscn`, `lantern_prop.gd`) on a bone through `Ability.show_on()`). Quaternius' `Idle_Torch` raises a torch in the left hand. Weapons can be stowed: hand parts name a `stow` marker (`ModularBodyPart.stow`, Node3Ds on an `UpperChestAttachment`: the one-handed weapon diagonal across the back, the two-handed one crossed the other way, the shield on the back), and `ModularModel.stow_weapons()` / `draw_weapons()` move them there and back. Animations call them through method keys (`Sword_Exit` stows, `Sword_Enter` draws; move the key in the animation to change the moment); the editor calls no method keys, so `Model` plays them itself there (Menagerie), and an animation that draws puts the weapons away as it starts (the knight spawns with his sword on his back).
`ModularModelParts.of(scene)` caches what a body scene offers (part names, slot parts, mesh options) for code without an instance. Saved types, catalogs and bodies store parts by number: only append new parts.

**Equipment** (`engine/objects/equipment/`, only modular bodies wear it):
- An `EquipmentLook` (a `Profile`) is a mesh combination that works: `type` + `appearance` (`EquipmentAppearance` → `EquipmentPartMesh`es: part, male mesh, optional female mesh) + an `allowed` flag. Items with stats and abilities will come later as their own resource referencing a look; until then characters wear looks directly.
- Generated looks live in one `EquipmentCatalog` per type (`data/equipment/catalogs/`), each stored inside the catalog under its combination key (`"21-00 00"` → sub-resource ID `21x00_00`, ResourceId `uid://<catalog>::21x00_00`; `00` stands for no mesh, matching the asset pack's bare `00` meshes, so all-`00` keys are empty and never generated). Unchecked looks stay recorded (`allowed = false`) to document the decision; new combinations are added checked, since most work and only odd ones are unchecked by hand. Toggling `allowed` emits no `changed`, so previews do not rebuild. Hand-made looks are files under `data/equipment/<type>/`. Sync and saves send `ResourceId`s; peers may only request allowed looks pointing into `EquipmentLook.ITEM_DIRECTORY`.
- `EquipmentType` (`data/equipment/types/*.tres`) decides the `model` it dresses (a body scene; `fits()`), the `slot`, the `parts` its looks set (numbers of that body's `Part` enum, listed by name in the inspector), `blocked_slots` (e.g. helmets block FACE) and optional `part_groups` (parts sharing a mesh number; the first part leads; `..._LEFT`/`..._RIGHT` pairs are linked automatically). A combination's key is one mesh number per linked group, e.g. `"05 03"` (`EquipmentType.get_combination_key()`). `EquipmentCombinations` walks a type's combinations on a `ModularModel` (leaders, partners keeping their mesh when they lack a number, `show_key()` to put a key back). `EquipmentLook.Slot` is stored by number in saved types: only append new slots.
- Each body decides which parts a slot owns (`ModularModel.get_slot_parts()`, `EquipmentType.get_reset_parts()`). `CharacterEquipment` (child of `Character`) holds one look per slot; equipping resets every part of the slot and its blocked slots, then applies the look, and is refused while another look blocks the slot or once a model is shown the look's type does not fit (dwarf gear on a human). Dwarf types: Dwarf Outfit (TORSO: body + shoulder pads), Dwarf Headwear (hides the hair), Dwarf Face Gear. Hand types exist per body (the dwarf's prefixed `dwarf_`): Weapon (MAIN_HAND part), Two-Handed Weapon (TWO_HANDED part, blocks OFF_HAND), Shield and Off-Hand Weapon (OFF_HAND_WEAPON part; its catalogs copy the weapon catalogs' looks); the main hand slot owns both weapon parts and the off hand slot the shield and the off-hand weapon, so equipping either of a slot's clears the other. `Character` re-applies body and equipment on every model rebuild.
- `CharacterProfile` has one starting equipment field per slot (`starting_head` … `starting_off_hand`; the export group hides the prefix), each holding an `EquipmentLook`: usually a copy stored in the profile (`set_starting_equipment_for()` copies looks from other files such as catalogs via `EquipmentLook.make_local()`), so characters are dressed part by part; hand-made look files are referenced. Stored looks are synced by their ResourceId into the profile file (`uid://<profile>::<id>`). Older profiles saved a ResourceId string under the plain slot name; `_set()` loads it as a copy. `random_equipment` rolls one `SpawnTable` per extra look. `create_character_data()` runs on the server only: it resolves the variation, takes the body the player picked in the lobby (`Player.body`, rolled by that player with `CharacterProfile.roll_body()` when picking a character and synced by the Player's synchronizer) if `ModularModel.is_complete_body()` accepts it, else rolls one (`ModelConfigurationRandom.roll()` → `BODY`, mesh IDs; peer-sent IDs are checked by file path against the part's meshes before loading) and equipment (`EQUIPMENT`, look IDs). Character data has 5 keys.
- Sync: `CharacterEquipment.equipped_ids` (`ResourceId`s) is replicated by its own `EquipmentSynchronizer`, pinned to server authority even inside a `PlayerController` (client) subtree. Peers call `request_equip()` / `request_unequip()`. There is no ownership/inventory check yet. Saves need nothing extra: spawner data already holds the IDs.
- Authoring happens in Menagerie (`addons/menagerie/`): the Gear tab shows looks grouped by type and base mesh with a checkbox per catalog look (unchecked = greyed; Space toggles the selection; Delete unchecks catalog looks and trashes hand-made files). The Equipment panel lists the types fitting the previewed body and steps through a type's parts (linked parts follow), checks the shown combination (`A`), adds missing combinations (checked), reviews them by keyboard (`Q`/`E` previous/next combination of the varied parts, `A` toggles; needs focus inside the panel), or saves hand-made looks. Toggles only set flags; `CatalogSaver` saves changed catalogs a second later, on leaving the Gear tab and on plugin unload. Characters are dressed in the inspector: a plugin replaces each `CharacterProfile` slot field with `EquipmentSlotProperty`, a type dropdown (types fitting the profile's model variations, `CharacterProfile.fits()`; starting from a copy of the type's first catalog look) plus one carousel per part stepping through that part's meshes (`EquipmentType.get_mesh_options()`, `EquipmentLook.with_part_mesh()`); left/right parts share a carousel until split, and Link matches the right side to the left. Choices go through `emit_changed`, so they can be undone and are saved with the profile; a blocking look empties the slots it blocks. The lobby shows every player's model (the local one at `CharacterPreview`, others on the scene's `OtherCharacterSpots` below their panels) with their synced body and starting equipment (`CharacterProfile.dress_model()`). Character previews keep their rolled body and random equipment across rebuilds, until the model scene changes (`CharacterProfile.setup_model(model, reroll)`); the preview's Randomize re-rolls.

Saving: `Serializer` collects `NodeSerializer`s (spawned nodes) and `PropertiesSerializer`s (e.g. `SynchronizerSerializer`: a synchronizer's spawn properties, such as the turn number). Passes are cleared on load (player ids differ between sessions).
